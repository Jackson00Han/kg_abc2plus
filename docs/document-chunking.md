# 上传切片配置

本阶段补齐上传页面到后端的切片参数、只读预览及任务记录。复用现有解析器、摄取、权限、本体校验、构建和审核流程。后续接通的 XML 抽取与通用文档自动复核见[实例构建验收](instance-construction.md)。

## 页面操作

在“知识构建 → 上传资料”的“来源信息与处理设置”中选择：

| 参数 | 默认 | 页面可选值 |
| --- | --- | --- |
| 每片长度上限 | 1,200 字符 | 800 / 1,200 / 2,000 / 3,000 |
| 切分方式 | 文档结构优先 | 文档结构优先 / 固定长度 |

不展开设置也会提交上述默认值。字符数指规范化原文的 Unicode 字符数，包含标点、空白和格式标记，不是 Token 数。

“预览切片”复用上传预检，显示实际片数、平均长度及最短/最长范围，不保存来源或调用模型。上传构建时再次执行相同配置的预检；完成后显示持久化任务返回的配置。修改参数会使页面中的旧预检确认及操作键失效；处理中锁定配置。

页面支持 UTF-8 TXT / Markdown / CSV / JSON / XML。XML 默认采用“按本体抽取”，也可以显式选择“仅保留来源”。文件选择器支持 `.xml`，前端接受 `application/xml`、`text/xml`、空 MIME 或通用二进制 MIME，统一提交 `application/xml`；扩展名与具体 MIME 冲突时拒绝提交。真正的格式校验由服务端解析器执行。

XML 复用默认切片、预检去重、来源保存及任务入口，无需用户先转换成 JSON。后台 XML 解析失败返回 `422 xml_input_invalid` 和固定中文提示，不输出原文或底层异常。只有抽取通过本体及精确证据校验的结果进入候选；“仅保留来源”不生成复核候选，页面明确显示原因。来源信息、访问组与现有发布边界保持生效。跨片拓扑和映射诊断的后续边界见[接入说明](document-mapping-preflight.md)。

## 切分行为

- 文档结构优先：普通文本复用段落/换行边界，XML 复用标签边界，JSON 复用记录边界；Markdown 合并连续短小节，大章节优先在段落、表格或代码围栏边界切分。能放入长度上限的完整表格和代码块尽量保留，超长块仍按硬上限切分。
- 固定长度：严格按字符上限切分，最后一片可以较短；可能切开句子、表格或结构化记录。
- 两种方式都保留无重叠、无遗漏的原文范围、校验和及确定性 Chunk ID。不会补写标题、表头或模型生成内容到原文中。
- 显式设置对 JSON 同样生效，不再被旧的跨记录 JSON 4,000 字符特例覆盖。旧请求继续使用原有 JSON 路径。
- 本次仅提供可配置切分，不声称某一片长已经达到最佳抽取质量。跨片证据和自动语义分组仍按后续建设计划推进。

## API 契约与兼容

`POST /v1/knowledge:preflight` 和 `POST /v1/knowledge:construct` 共用可选字段：

```json
{
  "chunking": {
    "max_chars": 1200,
    "strategy": "structure"
  }
}
```

`max_chars` 为严格整数，范围 800–3,000；`strategy` 仅接受 `structure` 或 `fixed`。传 `chunking: {}` 使用默认值。人工补充记录不接受切片参数。

省略 `chunking` 或传 `null` 的旧客户端保留旧解析行为、切分签名及操作指纹，以保证旧任务可重试；页面始终显式提交默认或所选配置。配置仅在单次解析中生效，不修改共享解析器，防止并发上传互相影响。

预检、构建响应及任务列表/详情的 `chunking` 摘要包括：

```json
{
  "max_chars": 1200,
  "strategy": "structure",
  "splitter_signature": "版本化切分签名",
  "chunk_count": 17,
  "min_chars": 755,
  "max_actual_chars": 1194,
  "total_chars": 17859
}
```

上例统计来自已授权 V11 模拟知识文档的本地预览，不是通用必需数量。旧任务的 `chunking` 为 `null`，页面不推测其配置。配置和实际统计参与预检确认凭据、构建指纹及不可变任务身份，并通过现有租户和访问组过滤读取。现有文档、片数、调用次数、超时及并发预算保持生效。

## 已保存来源的保护

当前 `DocumentVersion` 按来源内容确定身份，`HAS_CHUNK` 表示这一版本的一组不可变片段。改变切分策略不能直接给同一版本追加另一组片段，否则会破坏历史证据和发布成员校验。

因此本阶段的设置用于新上传的资料版本；同一来源、同一内容版本采用另一切分签名构建时返回 `409 construction_chunking_conflict`。工作流在模型和来源写入前检查，底层来源存储在既有文档写锁内再次检查，避免并发写入混合片段。原有 Chunk 不删除、不覆盖。已有版本重新切片属于后续版本契约工作，本阶段不自动重切用户资料。

此前来源接入验收时，V11 两份已保存资料为 32 + 84 个片段（之后用户已重置知识库，不代表当前库状态）。对相同文件执行只读新默认预览，XML 为 32 片，Markdown 为 17 片；这是新设置的预览结果，不代表已迁移现有资料。
