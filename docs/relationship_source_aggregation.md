# 同一关系的多来源处理

## 行为

同一租户、本体版本内，主体实体 ID、关系类型、方向、客体实体 ID，以及规范化关系属性和时间限定一致时，视为一个关系事实。实体名称、文档来源、原文位置、审核状态和来源等级不参与关系事实身份。不同实体、属性值或适用时间仍分别保留。

后端通过 `domain/facts.py` 生成版本化的 `fact_key`。审核比较、发布实例预览和图谱浏览共用此规则。新写入的关系来源断言及其导航投影保存该键；已有记录在读取时按相同规则计算，无需重建或覆盖历史数据。

关系事实具有唯一的逻辑身份；不可变来源断言仍是独立记录，不对来源断言施加三元组唯一约束。这样既能显示一条关系，又能逐条审核、引用、修正或撤回它的证据。未引入独立的全局关系节点或修改旧断言 ID。

## 审核与发布

- 关系审核比较当前有权访问的已发布权威及业务来源；属性审核沿用原有权威比较范围。
- 重复提示显示“确认并追加来源”，异步检查返回后同步更新按钮。批准只进入待发布状态，发布后才作为有效来源展示。
- 发布预览保留逐记录变更，并增加 `relationship_fact_changes`。最终实例按关系事实聚合，完整列出 `sources`、`evidence_ids` 和各来源等级。
- 同批相同关系即使审核时尚无已发布匹配，也在发布预览及发布后的图谱中聚合；候选队列仍逐条审核，不自动批准或丢弃重复候选。
- 撤回一条来源后，只要授权视图内仍有有效已发布来源支持，关系继续显示；最后一条有效来源撤回后不再显示。

## 浏览与权限

`graph:query` 先执行现有权限、文档生命周期、版本和精确证据校验，再聚合关系，最后分页。同一关系的来源不会被分页拆成多条边。

每条边增加 `fact_key`、`relationship_id`、`revision_ids`、`source_count`、`sources`、`authority_levels` 和关系属性。来源数量指可见的来源断言记录数，同一文档的不同证据位置可以是不同记录，不等于独立文档数。为兼容既有消费者保留的单数 `revision_id`、`record_id`、`authority_level`、`origin`、`confidence` 和 `source_kind` 只表示首条来源，不代表整个关系的统一评级。

普通知识浏览和工业图谱均使用关系事实键作为连线 ID。实线表示可见来源中含权威来源，虚线表示仅有业务来源；这不提升任何来源等级。来源详情每页最多读取 10 条，可翻页查看，其权限和版本校验继续由证据 API 执行。维护入口展开所有来源记录，允许逐条修正。

原有 500 条授权记录读取上限保留；不会因为聚合而放宽读取预算。回答引用和检索证据继续保留来源断言，本次不改变检索评分或回答生成算法。

## 后续修正：单值属性的多来源阻断发布

用户反馈发布预览返回 409。对当前本地资料的只读诊断发现，同一设备的 `EquipmentCode` 与 `RatedPower` 各有两条来源，规范化语义各只有一个；旧发布校验按来源断言条数计算单值约束，因此错误拒绝发布。这不是已证实的并发修改。

摄取批次、完整发布清单和已发布图谱质量检查现统一按规范化属性语义的不同值计数，保留类型、单位和时间限定。多来源同值通过，不同值仍拒绝；无规范化语义的历史或无效记录仍独立计数，不借去重绕过校验。属性界面和证据仍保留独立来源记录，本次没有扩展为属性显示聚合。

质量规则版本更新为 `published-governed-graph-quality-v2`，历史报告不改写。通用 409 提示改为“版本、依赖或知识约束校验未通过”，避免将知识约束失败一概描述为并发冲突。

轻量验证：三个针对性测试通过，覆盖同值多来源通过、不同值阻断及原有格式校验。在当前本地数据库上使用新代码为 8 条已审核记录执行一次 `preview_only=True` 的回滚式预览成功，输出 4 个实体、4 条属性来源记录、3 个关系事实；确认生效发布仍为第 1 版、已审核记录未变化。未实际发布、未重启正在运行的后端，也未执行完整回归或生产验证。运行中的后端需重启以加载 Python 修改。

## 发布错误直接定位到现有候选列表

发布预览及正式发布的已知校验失败，通过 409 响应的可选 `publication_issue` 返回固定原因和相关记录位置。支持属性值或格式问题、缺少必填属性、关系数量超限、关系附加属性问题、缺少实体来源依赖、替换记录要求，以及发布版本或预览变化。一次显示当前首先遇到的问题，最多列出 50 个位置，超出时明确提示；未覆盖的异常保留通用错误与请求编号，不猜测问题记录。

候选列表为每条来源记录增加定位标记。失败时在原列表标红相关条目、展开其所属折叠区域，在错误说明中提供“定位问题”按钮。用户继续使用原有“返回修改”入口，无新增审核流程，也不自动改变勾选、批准或发布状态。缺失必填项定位到对应实体；不在当前候选列表的记录明确提示在已有知识中核对或刷新，不误标同实体下其他来源。重新选择、刷新到不同候选版本、重新预览或切换身份会清除旧提示。

错误详情只由已完成授权读取的发布记录生成，固定原因不直接使用数据库异常文本；普通错误响应保持原有结构和脱敏行为。前端按顶层错误响应字段读取详情并转义显示。

## 人工确认为独立事实

属性和关系审核增加“作为独立事实确认”。当实体依赖和比较信息可用时，审核人可以不接受重复或冲突建议，填写 1–2000 字的区分理由后单独确认。缺少理由、取消填写或仍在编辑时不提交；实体依赖未完成、比较不可用或记录版本已变化时不能绕过检查。

审核 API 使用 `fact_action: INDEPENDENT` 和 `fact_reason`，仅允许不同时编辑内容的单条事实批准。批量 API 可包含多个各有独立理由的决定，但界面逐条确认。服务端在原有锁和权限边界内重新检查依赖及比较状态，继续验证证据、本体和端点。

独立决定作为 `FactDistinction` 保存在不可变来源断言修订中，包含所属记录 ID、理由、审核人和时间，使用 `fact_distinction_json` 持久化。后续普通修订及发布保留该决定；关系事实键包含这条记录的人工区分标识，因此相同三元组也不会再次被自动聚合。属性本来就逐来源保存，现在同时保留并展示独立决定。独立事实不再作为其他候选的自动重复合并目标。

该决定属于审核元数据，不改写来源原文，不提升来源等级，也不把人工理由作为文档已证实的条件。审核页、发布预览、知识详情和来源详情显示“人工独立事实”，明确区分依据尚未结构化。独立性绑定当前来源记录；新的来源记录不会仅因原文相同就自动归入这个独立事实，仍需重新审核。本次不提供跨记录的人工独立分组或撤销独立决定的专门操作。
