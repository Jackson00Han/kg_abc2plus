# 累计发布容量验证（2026-09-13）

## 变更边界

单次发布的新增、移除和替换变更合计上限仍为 500 条。当前发布版本累计清单使用单独的 2,000 条上限；不能只修改写入端而让正式读取、完整成员校验、预览、层级约束或 API 响应继续拒绝大于 500 条的有效版本。发布事务和读取的既有时限、权限、证据以及完整性要求均保持。

此前 500 条同时约束单次变更与累计清单。因新版本默认保留旧版本全部记录，300 条后再新增 279 条也会在最终 579 条检查处失败；分批只能改变单次输入量，不能绕过累计上限。此问题是当前整份资料成功抽取后进入后续审核发布的实际容量限制。

## 代表性真实服务路径

新集成测试 `tests/integration/test_publication_capacity_neo4j.py` 只使用已授权循环水泵演示台账中的一条设备句，重复生成两个隔离测试来源：100 次与 93 次原句，分别 8,100 与 7,533 字符。每次原句形成一个设备提及、一个设备编码属性和一个 37.5 kW 额定功率属性，共 300 与 279 条治理记录。每次提及和属性有各自稳定记录 ID 与精确原文位置；同一句的重复出现不声称多台设备或更多实际事实。

测试依次经过正式文档解析器（8 与 7 个连续片段）、不可变来源摄取、类型化属性规范化、权威专家实例导入服务、两轮发布预览与实际发布，再通过当前发布读取、来源资料库和正式检索引擎检查累计 579 条和两份来源。没有手工构造发布清单，也没有直接设置数据库记录为通过审核来替代上述服务。

断言包括：

- 单次传入 501 条仍拒绝，且没有活动发布。
- 首次预览与发布为 300 条，第二次为 579 条，两个阶段 manifest hash 一致。
- 第二版仍包含首版所有记录、两份来源及全部 15 个原文片段。
- 正式检索分别按每份来源过滤，仍能在第二版读到原文且引用位置精确。
- 同一配置的成员校验另用既有 14 种安全场景检查 2,000 / 2,001 条边界。

复现命令：

```sh
sh scripts/run_stage8_neo4j_tests.sh .local/whole-document-extraction/publication-capacity-final.json .local/whole-document-extraction/publication-capacity-final test_publication_capacity_neo4j.py
```

容量模块通过 `load_tests` 在同一一次性服务器中顺序运行容量用例及既有成员守卫矩阵，避免重复启动和并行争用。成员守卫也可单独以 `test_publication_member_guard_neo4j.py` 作为脚本模式运行。

## 结果与限制

离线容量及相关回归最终执行 100/100 容量、发布、图读取与 API 检查，以及 103/103 正式检索、来源、权限及相关检查，共 **203 项通过**。包括累计清单与已发布知识清单累计计数的 2,000 条响应边界；单次变更及清单每页仍为 500 条。日志分别为 `.local/ontology-source/publication-capacity-unit-final.log` 与 `publication-capacity-regression-final.log`。数据库 IO 使用离线替身的检查不当作真实数据库结果。

首轮真实服务已完成 300 与累计 579 条的预览、发布、活动版本读取和两份来源列表。正式检索前发现新测试夹具使用 `top_k=2` 与默认 `anchor_k=3` 不兼容，尚未发出检索查询；该轮因此没有通过整套验收。修正为 `top_k=2, anchor_k=2` 后，在另一全新隔离数据库完整重跑，并并入成员矩阵。生产检索、发布时限及安全断言未作修改。

最终真实 Neo4j 5.26.12 联合回归 **2/2 通过**，用时 **235.239 秒**，零失败、错误或跳过。第一项经过完整 300 + 279 服务链路；第二项是既有 14 种成员边界子场景，含新的 2,000 条合法与 2,001 条拒绝、缺失/额外/替换/重复成员、跨租户、其他本体、候选状态、错误标签及空来源清单兼容。最终结果文件为 `.local/whole-document-extraction/publication-capacity-final.json`，完整日志为同目录 `publication-capacity-final.log`。

上述是单次开发规模观察值。来源准备包含多个服务步骤，不是一次发布事务；正式检索也包含其既有的多个有界阶段。发布仍使用原 30 秒事务预算，来源列表仍使用原 15 秒读取预算，检索使用原配置。没有提高超时、降低安全断言或省略来源来获得通过。脚本结束后已确认拥有的一次性容器清理完毕。`git diff --check` 通过。

本测试采用 4 维确定性嵌入，不调用外部模型。579 条来源记录最终对应一个设备及两项多来源支持的属性，覆盖累计清单容量和证据保留，不能代替大量不同实体、复杂关系或完整 2,000 条发布负载验证。2,000 / 2,001 的成员矩阵只验证有界读取守卫，不证明 2,000 条真实记录可在现有发布时限内完成。所有写入均位于一次性隔离 Neo4j；没有向用户 8002 数据库写入或发布候选。
