## 三个实际失败原因

| 样本 | 原始输出与失败 | 含义 |
| --- | --- | --- |
| ordinal 8，法兰 `BUS1.S1.FE1`，第一次尝试 | `project_id` 的证据声明为 `"asset_ref": "PBMBaseProj_2512/BUS1.S1.FE1"`，填写 `[19,51)`；实际该范围从冒号开始，完整字段起点为 8。产生 `EVIDENCE_SPAN_MISMATCH`。 | 模型将字段文本与值附近的边界混用；完整字段范围提示有帮助。 |
| 同一 Chunk，第二次尝试 | `full_name` 证据 `[260,292)` 已逐字匹配，但实体提及仅在 `[190,201)`、`[248,251)`，产生 `ENDPOINT_OUTSIDE_EVIDENCE`。ordinal 14 插接箱 `PIU4` 也把证据向后扩至 817，却遗漏前方 `[226,230)` 的实体提及。 | 只修字符索引不够；属性证据必须同时包含所属实体提及和值。 |
| ordinal 14，插接箱 `BUS1.S1.PIU4`，第二次尝试 | `source_annotations` 的 `raw_literal` 把原文多行 JSON 改成紧凑单行 JSON，产生 `FACT_TOKEN_OUTSIDE_EVIDENCE`。 | JSON 语义相同不代表逐字来源相同；须先逐字保留原值，再由规范化层解析。 |

现有 token 提示确实会在 `/`、`.` 拆开完整设备编码，但不能据此断言它是上述所有失败的根因。此次原始审计更直接支持“字段和值范围混用、未包含所属实体、重排 JSON 空白”三类问题。

## 可复现离线检查

原始审计保存在 `.local/ontology-source/topology-two-failed-audit.json`；该文件是获授权开发诊断快照，不是新增知识来源。执行：

```sh
.venv/bin/python .local/ontology-source/analyze-json-spans.py
```

脚本仅读取本地两个样本和已授权源本体/目录，机械计算 JSON 字符串、完整字段、字段原值及对象/数组边界，断言每个范围逐字对应 Chunk。随后创建独立的**合成响应副本**：属性证据使用同时含实体和值的完整对象；嵌套 JSON 只恢复原文空白，保持解析后的值相等，再交给现有严格校验器。不写回数据库、不改变原始响应、不产生候选。结果输出 `.local/ontology-source/topology-span-feasibility.json`。

| 样本 | 完整对象范围（Chunk 相对字符，右侧不包含） | 字符串 / 字段提示数 | 原第二次尝试拒绝数 | 合成副本拒绝数 |

## 下一提示版本建议

建议在下一独立提示版本新增通用、数量和字节均有界的 JSON 字符串/字段/容器范围提示，保留现有严格校验：

1. 明确区分完整字段范围、原始值范围、字符串内容范围，均使用 Chunk 相对、0 起点、右侧不包含的原字符索引。转义字符串的 decoded 值不能替代原文作为精确证据。
2. 要求属性证据选择同时包含实体提及和值的最小已提供容器；关系证据必须包含两个端点提及。没有共同范围时不凭模板补造关系。完整对象可作为受 Chunk 大小约束的保底选择。
3. 嵌套对象/数组的 `raw_literal` 逐字复制原值；规范化仍由现有处理层完成。提示只提供定位，不增加事实或自动确认来源。

原始整份任务继续使用其原有 v6/请求指纹。新版本需先在这两个受限样本开展真实模型对照，保留所有原始响应与失败；通过后再决定后续任务是否采用。当前任务“整份处理”不等于每个 Chunk 都产生可发布图事实，拒绝和候选数应分别报告。
