# JSON 上下文属性映射与增量补全

## 问题与实现

设备对象位于数组中，而所属项目等共享属性位于根节点或父级对象。原有逐条字段映射只能处理记录内部字段，因而遗漏了本体要求的上下文属性。新增通用的声明式映射阶段：根据当前本体、已有字段映射、完整来源身份及根/父级上下文，由模型提出字段映射，程序逐对象验证后形成候选事实，再进入现有自动审核。

该实现不匹配文件名，不硬编码 `project_id`、母线槽或项目名称。JSON 路径、属性名、实体类型及身份模板均来自输入与已发布本体。模型返回有界 JSON 配置，不生成或执行脚本。

执行顺序：原有解析/字段映射与抽取 → 上下文映射及逐条证据校验 → 实体身份审核 → 属性及关系审核 → 人工处理未决项 → 现有发布流程。

## 判断边界

- 只补尚无局部映射的属性。已声明局部映射的字段即使为空，也不能因此认定应继承默认值；不把未连接端口等合法空值变成虚构事实。
- 局部明确写出的 `null` 或空字符串也不自动覆盖。身份模板中的上下文变量不能被同名记录变量替换，防止把另一项目的对象误绑定到当前项目。
- 若来源声明身份模板，程序使用上下文值和记录字段展开模板，必须与完整来源身份完全一致。没有模板时，仅允许模型确认语义明确的父级默认值，随后仍需事实语义审核。
- 上下文来自目标集合的根/祖先作用域；其他项目的兄弟分支不能成为全局默认值。局部值冲突、身份不一致、多个候选规则和缺失证据均保留问题，不自动覆盖。
- 模型调用最多两次、单次超时不超过 60 秒。失败显示未完成；无依据的映射不能以确定性事实进入发布。
- 模型提出的规则逐条校验：不适用或不符合本体的规则记录在映射审计中，不连带丢弃独立有效规则；有效声明仍须通过全量对象校验与独立事实审核。
- 单次编译复用解析后的不可变 JSON 树与各集合上下文，循环检查任务时限；持久化及审核仍独立重新校验证据。

## 双证据与幂等

每个新增事实保留两处位置：主体记录原文证明对象归属，根/父级标量原文证明值的来源。两者必须属于同一租户、文档版本、快照与访问策略；保留来源和映射校验和、JSON Pointer、身份模板与审核历史。确认、发布、证据读取均重新校验，不能通过切换证据位置绕过主体范围校验。

上下文输出使用独立、不可变的 `KnowledgeContextProjectionRun` 清单与稳定记录 ID。原构建任务的 Chunk 回执不重写，原有人工决定及已确认版本不覆盖。重试读取已有清单、恢复已写入记录，不重复抽取或重复建事实。模型映射审计与事实审核审计分别记录，不混淆模型调用数。

空清单允许用户显式重试后生成新的不可变清单，保留原尝试。已计划非空输出的清单始终固定回放，包括已经写入事实、但进度回执尚未落库的情况。同任务最多 16 份清单，写入前检查上限；事实 ID 不随清单代次改变。

工作台增加“补全上下文并审核”，完成后重新读取当前任务，同步构建回执、人工队列提示及后续操作。上下文摘要独立展示，可分别查看实体原文和上下文字段原文。

同身份、同任务、同审核轮次的并发详情请求合并，结束后立即清除，修复终态强制读取新结果。轮询使用服务器回执代次过滤旧完成状态，不依赖客户端时钟。回执仍优先展示不确定项，在同一状态内优先展示本轮新决定，使新增上下文事实的双证据可见。

## 验证

当前真实库修复前基线为 1,208 条已确认记录（310 条提及、898 条事实），20 个不可变 Chunk 回执。基线文件 `.local/context-projection-baseline.json` 只保存 ID 与校验和。

只读真实模型探针在收紧映射范围后形成 24 条 `project_id` 候选，全部通过逐条来源身份模板校验，未产生上下文冲突。探针只验证计划，没有写入知识库。

可复现命令：

```sh
.venv/bin/python -m unittest tests.unit.test_context_mapping tests.unit.test_context_mapping_api tests.unit.test_schema -q
sh scripts/run_stage8_neo4j_tests.sh .local/context-projection/result-verified.json .local/context-projection/observations-verified test_context_projection_neo4j.py
sh scripts/run_stage8_neo4j_tests.sh .local/context-contract-optimized/result.json .local/context-contract-optimized/observations test_context_contract_neo4j.py
.venv/bin/python scripts/verify_context_projection_result.py --baseline
```

基线命令只可在修复前执行一次，拒绝覆盖已有基线。隔离 Neo4j 用于写入、发布与权限故障测试；真实库只对用户授权的原任务增量补全，不自动发布实例。

双证据真实 Neo4j 合同测试最终 3/3 通过，包含实际发布、质量检查、图检索/浏览的第二引用、次证据 ACL 变化、来源退休与篡改拒绝：`.local/context-contract-final/result.json`。初版发布事务曾因查询规划超过 30 秒而失败，修复后重跑通过，没有提高超时上限。

性能调整复用已经授权的外层来源边界，并以 `WITH DISTINCT` 分隔主查询的来源与本体连接。强制重新规划的单次定位对照为无上下文 0.464 秒、修复后完整校验 2.193 秒；并行负载下其他查询形态为 7.884–13.590 秒，不能据此承诺固定延迟。完整诊断与查询指纹见 `.local/context-query-planning.json`。临时比较过官方文档中的规划选项，仅用于定位；最终代码不依赖已弃用选项。方法参考 [Neo4j 查询调优文档](https://neo4j.com/docs/cypher-manual/current/planning-and-tuning/query-tuning/)。

当前新增映射阶段适用于已建立结构化字段映射的 JSON 对象集合。XML、普通文档及未获确定来源映射的输入仍沿用各自流程；不能将本次实现表述为任意文件都能自动完成上下文继承。

## 真实库修复结果

在当前母线槽知识库的原构建任务上点击“补全上下文并审核”，没有重传或修改原文件。最终成功请求耗时 78.905 秒，新增 24 条 `project_id`，均通过程序身份与双证据校验、真实模型事实审核。当前结果为 139 个实体组、310 条提及、922 条事实自动通过；人工项、阻塞项、未完成项及映射问题均为 0。此次时间为单次本地实际观测，不是生产性能承诺。

`.local/context-projection-acceptance.json` 的 26 项只读核验全部通过，确认原有 1,208 条记录的当前版本属性、20 个 Chunk 回执及原文件校验和完全不变；新增事实恰好对应所有 24 个资产，并保留两处精确、同权限的原文证据。

首次映射尝试包含不符合本体的独立规则，纠正后曾返回空清单。修正逐规则校验与空清单显式重试后完成上述修复。先前清单和模型审计继续保留，不能将第一次空结果称为成功补全。最终增量事实审核使用一次模型调用；上下文映射审计累计三次调用，包含之前的两次尝试。

重启后的独立 Chromium 在 1280、1440、1920 三种桌面宽度验证构建回执、映射展开、原文入口及空人工队列；两种证据角色的 API 返回与原文字符位置一致。最终检查通过，保留 12 张截图并实际查看了三个宽度的渲染与滚动位置。真实浏览器记录位于 `.local/browser-qa/context-projection-inspect/`，修复操作记录位于 `.local/browser-qa/context-projection-success/`。后续检查只读，禁止再次修复或发布。

选择已确认的 Project 提及和其六条属性，共七个版本，调用现有发布预览接口返回 HTTP 200 并生成受治理清单 hash。该验证仅覆盖此选择集的真实预览；没有发布用户实例，也不代表已预览全部实例。

实际原文查看还暴露了历史查询首次规划慢的问题。精确限定记录并分段连接来源、本体后，同一真实记录的事实历史冷查询从 34.023 秒降至 1.982 秒，前后两条完整历史记录 hash 相同；详细只读观测见 `.local/context-history-performance.json`。这同样是定位用的单次对照。
