# Representative Development Corpus

`dev-corpus-v1` is the bounded corpus used between the minimal teaching
fixture and the production-reference validation workload. It exists to expose
multi-document, temporal, identity, and authorization failures early without
making every development check depend on provider calls or a deployment-sized
database.

## Composition

The versioned corpus contains 10 repository-authored synthetic English company
filings:

- two logical tenants;
- five company identities, including an intentional homonym non-merge case;
- FY2023 and FY2024 filings for each company;
- 12 exact, contiguous Chunks per filing, for 120 Chunks total;
- public/research and restricted access groups;
- exact values, changing values, graph relationships, and material that must
  remain unavailable to unauthorized principals; and
- versioned questions covering every Stage 1 question class.

Every manifest entry records stable source metadata, immutable checksums,
exact Chunk character ranges, deterministic embeddings, and expected evidence.
Every Chunk repeats its canonical company name, ticker, and fiscal year so the
evidence remains interpretable after bounded retrieval removes document-level
surroundings.
The source URIs use the
`urn:sample-graphrag:synthetic:dev-corpus-v1:` namespace so synthetic content
cannot be mistaken for an external regulatory filing.

## Reproducibility

The committed files are generated by one deterministic builder:

```bash
uv run --locked python scripts/build_dev_corpus.py --check
```

`--check` rebuilds the corpus in memory and fails on a missing, extra, or
byte-different committed file. Maintainers may intentionally regenerate an
updated version with:

```bash
uv run --locked python scripts/build_dev_corpus.py --write
```

Changes to content, identifiers, questions, or the generator require a new
dataset version or an explicitly reviewed correction with updated checksums.

## Validation use

Fast unit tests continue to use minimal fixtures. Stage 5A additionally loads
the complete corpus into a disposable Neo4j instance, verifies all 120 Chunks,
activates the deterministic embedding generation, executes representative
retrieval cases, and verifies tenant/access filtering and stable citation
round trips.

The fixture query vectors are projected from adjudicated evidence clusters.
They deliberately isolate ranking, graph expansion, context assembly, and ACL
behavior from an external embedding provider. The manifest therefore declares
`quality_claim: none`: these vectors cannot establish embedding-model or
customer-corpus quality.

The corpus satisfies the `dev-mini` minimum of 100 Chunks. It does not satisfy
the production-reference 10,000-Chunk workload, does not measure external
embedding or LLM behavior, and is not customer-corpus quality evidence. Those
limitations remain explicit inputs to Stage 8 and Stage 9.
