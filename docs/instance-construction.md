### 常规上传与治理步骤

1. 上传并诊断 YAML / JSON 本体，保存规范 JSON，显式启用版本。
2. 上传 UTF-8 TXT / Markdown / CSV / JSON / XML，预检来源、访问组和切片参数。默认按文档结构切分，每片上限 1,200 字符。
3. 选择“按本体抽取”后，已加载的有效声明式映射由程序执行；普通资料调用模型。程序校验类型、方向、值、单位、精确原文范围及关系端点；通过后保存候选和形成审计。选择“仅保留来源”时，不生成候选，页面明确说明。
4. 复核读取原文，先处理身份，再逐条审核属性和关系。普通候选可执行有界模型预审；明确授权的映射可独立重放复核，再通过既有治理服务审批。程序复查证据、约束、冲突和写入版本。身份不明、证据不足、冲突或复核未完成的记录留在待办。
5. 管理员选择已确认记录，查看完整发布预览，再执行发布。现有发布服务构建可访问的实例图谱、证据入口和版本记录。

自动复核不自动发布，也不提升来源等级。不同来源的同名对象不会仅凭名称合并。上述流程属于现有知识治理层，不引入设备专用公共逻辑。

## 本轮必要修改

- 删除普通 XML 上传只能 `SOURCE_ONLY` 的限制，复用已有逐片构建接口和解析器。
- `XmlChunkOntologyExtractor` 在完整 XML 安全解析后，为当前片段提供精确标量和起始标签位置。它只补充定位提示，不把标签包含关系解释成电气连接，不把组态、点地址或模拟数据解释为实测值或已发生故障。
- 对模型原样引用且在当前片段仅出现一次的文字，可修正其数字位置；文字不改写。重复引用、改写引用和越界端点继续被拒绝。原始模型响应保留在受保护审计中，定位修正有独立发现码。
- 自动复核策略升级为 `evidence-auto-review:v3`。普通文档候选获得有界原文上下文，不再因为缺少声明式 JSON 映射而全部直接转人工。候选分组不是稳定身份的证明，未审核属性不得作为强身份键。普通文档每条事实分别审核；已有经过验证的 JSON 声明式映射路径继续保留。
- 事实审核核对文档、版本、Chunk、端点实体与引用提及，关系证据必须同时包含两端的实际提及。写入继续使用既有租户、ACL、CAS、审核修订和发布服务。
- LLM 上传预检显式检查本体临时身份命名空间兼容性，返回 `construction_ontology_incompatible`，不静默修改本体；禁止实例化的抽象类型不要求临时实例命名空间。
- 模型错误按 SDK 异常类型及固定错误码区分连接中断、超时、模型额度、账户欠费状态与权限问题；不输出服务商原始错误正文，不据此自动重试或切换模型。
- 页面区分“来源保存未抽取”“抽取被校验拒绝”“待人工确认”和“已确认可预览发布”，XML 默认使用抽取流程。

完整本体下密集 XML 片段的单次调用实测约 53 秒，原 60 秒上限在批量运行中多次超时。因此本地 `workbench-construction.v2` 的单次抽取超时调整为 120 秒，总任务时限、256 次调用与各项证据约束不变。随后将本地抽取并发从 4 降为 2，以验证并减少当前模型接口的批量排队与超时；并发调整不改变模型请求和证据策略，不更换既有任务身份。配置变化会产生新的构建审计，原记录保留。

## 提取输入与 XML 证据引用优化（2026-09-21）

### 问题定位与设计依据

通过认证的当前母线槽任务读取及有界 Neo4j 只读审计，再次核对上述 21/32 片的任务。
42 次尝试中，40 次校验拒绝、1 次形成候选、1 次额度错误。36 次响应出现
`ENDPOINT_OUTSIDE_EVIDENCE`，24 次出现 `EVIDENCE_SPAN_MISMATCH`，可在同次响应中并存。
主要问题是模型既要提取语义，又要抄写整段 XML 和计算字符位置；大量冗余位置提示
及重复本体定义进一步增加请求开销。扩大切片没有直接解决这种输出负担。

参考以下公开实现与官方说明，采用“模型选择语义，程序处理精确来源位置”的分工：

- [Google LangExtract](https://github.com/google/langextract) 将提取结果映射到来源位置。
  本次借鉴提取与定位分工，使用现有 XML 解析器建立精确引用，不引入模糊匹配或新依赖。
- [Anthropic 上下文工程](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
  建议保持完成任务所需的高信息量上下文。本次无损合并重复定义，保留类型、方向、单位、
  基数、描述与属性约束，没有按关键词裁掉本体类型。
- [Google 结构化输出说明](https://ai.google.dev/gemini-api/docs/structured-output)
  强调应用仍须校验值；[百炼结构化输出说明](https://help.aliyun.com/zh/model-studio/qwen-structured-output)
  区分 JSON Object 与 JSON Schema。本次保留既有模式选择，不自动切换模型或假定模型支持严格 Schema。

### 实现与兼容边界

- `construction/prompt_context.py` 为完全相同的属性定义分配局部引用。同名但单位、约束、
  基数或描述不同的属性仍分别定义；`constraints_json` 在模型输入中展开为 JSON 对象。
  这些都是请求表示，存储本体及其校验和不变。
- 普通文本的位置提示改为 `[start,end,text]` 表，每个原有 token 及重复出现位置均保留。
  XML 使用专用标量和开始标签目录，不再同时发送逐 token 的重复位置表。
- XML 的每处标量与开始标签都有片段内 `x` 编号；`source_scope` 绑定来源校验和、片段文字、
  范围、Chunk、文档版本及租户。模型用 `span_ref` 指定实体提及；`quote=null` 表示整个标量，
  非空 quote 只能选择该标量内部唯一、未改写的子串。
- 属性和关系证据用 `start_ref` / `end_ref` 明确选择连续范围。程序从原始规范文本截取，
  不拼接零散证据、不补写祖先、不自动扩大证据。未知编号、反向范围、错误 scope、混合
  字段和歧义引用被拒绝。标量的 `opening_tag_ref` 仅提供位置，不能作为归属或连接事实。
- 还原后继续执行原有类型、实体端点、原文、值/单位/时间、属性基数和置信度校验。
  端点缺失、跨片归属缺失、身份歧义和模拟内容的真实性边界仍未自动解决。
- XML 纠错反馈改用引用契约，至多提供 16 项错误定位并明确是否截断；原有至多两次调用、
  超时、失败审计、额度错误停止、审核与发布边界不变。原始模型响应仍原样留存。
- 请求策略升级为 `ontology-extraction-request-v3`，XML 为
  `xml-chunk-extraction:v4-source-refs`。通过现有请求签名进入任务身份；新策略须使用新的
  构建操作，不能作为旧任务的同策略重试。旧数字位置响应仍可严格回放，不覆盖旧任务或证据。
